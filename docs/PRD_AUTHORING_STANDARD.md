# Project Sora PRD 开篇规范

生效：2026-10-30。用户要求适用于所有现行模块及配套系统设计。开篇必须让不了解内部缩写的读者看懂职责和工作因果，不以一句抽象定义、形容词或历史通过数代替解释。

## 开篇必须回答的问题

| 问题 | 必须说明 | 不合格写法 |
| --- | --- | --- |
| 这是干嘛的 | 用具体对象、动作和边界解释职责 | 只说“智能、连续、可调节的中枢” |
| 为什么要独立存在 | 没有它会出现什么真实问题，为什么相邻系统不能代替 | 只说“提升体验”“生产级必备” |
| 接受什么 | 哪个上游、何种事件/请求/Frame，最低必需来源与权限 | 只罗列系统名字或写“上下文” |
| 输出什么 | 具体结果/状态/协议、谁消费、会改变什么 | 只写“赋能下游”“情感输出” |
| 如何得到结果 | 输入经过哪些核心处理、谁解释、谁确定性计算、谁提交 | 把目标描述再次复述一遍 |
| 何时运行 | 当前轮读取、提交后异步、定时/显式治理或纯设计期规范 | 把所有组件画成每轮串行LLM |
| 对整体的意义 | 沿上下游解释最终用户能感知的差别 | 只列内部类名和协议版本 |
| 不负责什么 | 所有权、权限限制与当前实现/目标的区分 | 把设计存在写成服务已部署 |

开篇采用连贯职责/价值说明、适量输入输出表、一个有因果链的例子。结构可一致，内容不得把另一模块的名词替换后套用。正文算法、接口和验收条款继续展开，不用开篇摘要取代详细设计。

## 对承诺给出机制依据

“有来源、可持续、会衰减、可调节、可重评价”等每个关键承诺，都要映射到具体数据、状态或算法：来源引用如何保留、跨轮状态存在哪里、时间如何推进、什么限制变化、错误解释如何修订。不能仅用“使用LLM”解释全部能力。

例子应是面向任意用户的说明性场景，不硬编码开发者、仓库、飞书或GitHub工作流为产品规则。不展示未经验证的精确模型输出/评分，不承诺固定台词，不用虚构经历证明功能。

## 状态与编辑规则

先解释模块，再放工程状态或历史迁移记录。未实现能力明确使用“目标/规划”，当前代码、可配置适配器、默认接线、界面完成、安装验证和正式发布分开说明。旧文档引用的版本/通过数是历史证据，不随摘要修改而变成当前验收。

修改现有PRD前读取当前版本；仅修改批准范围，保护原正文、引用、资源与架构图；写后读回验证文本、位置、链接和资源。统一规范由本文件维护，当前PRD入口在docs/PRD_INDEX.md，版本和回执登记到artifact目录及工作流。
